# Timing, scheduling and memory

The game uses only CLK_50M. Rational accumulator enables produce CPU/PSG 3,072,000 Hz, MSM 384,000 Hz, pixels 4,915,200 Hz. Adjacent enable gaps are respectively 16/17, 130/131 and 10/11 system clocks; accumulated phase error remains below one 20 ns system clock. These rates are long-term exact for an exact 50 MHz source. `CPU_CE_PHASE` and `VIDEO_CE_PHASE` are elaboration parameters for controlled phase experiments; both production defaults are zero.

The provisional raster is 320×256 at 60 Hz, horizontal rate 15,360 Hz. Active x=0..255, y=16..239. Positive HS spans x=272..303, VS y=244..247. NMI is generated at x=316,y=239, four pixel periods before the active-to-blank edge. `NMI_X`, `NMI_LINE` and `FRAME_ORIGIN` permit controlled NMI placement experiments; the production frame origin remains y=240. Reset and the capture frame origin use y=240, preserving the measured interrupt/CPU startup relationship. The earlier NMI_LINE=240 experiment reset at y=0 and is a different timing profile; its reports are historical. It is emitted if enabled, held low through two CPU enables; TV80 sees one falling edge. The RGB, sync, blanking, pixel enable and debug coordinates are delayed together by four register stages including memory reads. Reset currently restarts the native raster. No fabricated PCB measurements or PLL validation are implied.

Renderer work per line: 64 tiles × (six fetch states + eight draws) = 896 clocks; 16 sprites × worst-case (nine record/test states + two ten-cycle row/draw groups + next) = 480 clocks; one completion = 1. Total 1,377 clocks versus at least 3,255 available. Background 0 overwrites every pixel, so no line-clear pass is required. Each ping-pong line has validity and a Y tag; invalid lines produce pen zero. Rendering samples live VRAM for the following line; there is no frame snapshot. Game flip is latched per rendered line. A sticky deadline error is exported and checked in simulation.

Program storage 49,152 bytes; graphics 40,960; sample ROM 16,384; PROMs 544; RAM 16,384; two 256×9-bit composed lines 576 bytes. Logical total 124,000 bytes = 992,000 bits. Five 8 KiB graphics plane memories return one row in parallel at a common address; this is banking, not duplication. CPU uses one synchronous program-ROM read port, RAM CPU read/write port and renderer read port. ROM download uses the write port while CPU is held. Palette colour and lookup are separate memories. No external SDRAM is needed by game storage. Physical block packing, logic overhead and timing remain unknown until a future fitter run.

Inferred memories use one-clock reads and old-data same-edge collision semantics in RTL. RAM clear takes 16,384 clocks (327.68 µs); clear wins over CPU writes. No array reset is used. FPGA implementation of dual-port read-during-write must later be confirmed; software/video reads near CPU writes are a documented timing abstraction. TV80 read responses are retained through the next enabled edge because its bus control outputs and internal di_reg run at the fast system clock around CE-held T states. READY is not wired to CPU WAIT without board evidence.

The original Template platform PLL source is retained because its QIP references it, but the game bypasses that PLL and uses CLK_50M. Platform audio/HDMI PLLs remain unchanged. No normal development command runs Quartus.

Executed Quartus 17.0.2 fit: full sys_top uses 10,095 ALMs (24%), 202 M10K blocks (37%), 1,507,777 block-memory bits (27%) and 34 DSP blocks (30%). Four-corner TimeQuest has minimum setup +0.085 ns and hold +0.086 ns; the slow-corner game/system 50 MHz clock setup margin is +4.870 ns. All clocks are constrained, but inherited external I/O constraints omit 5 inputs and 50 outputs. These timing results are conditional on the existing constraints and do not establish complete HDMI/board timing closure. See reports/quartus_review.json and detailed corner reports.
